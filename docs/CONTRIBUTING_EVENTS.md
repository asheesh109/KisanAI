# Contributing During GSSoC & Hacktoberfest

Welcome to **KisanAI**! This guide is intended for contributors participating in **GirlScript Summer of Code (GSSoC)** and **Hacktoberfest**. It provides a quick reference for contributing effectively during these programs while pointing you to the project's detailed documentation.

> **Note**
> This guide complements the existing documentation. Before contributing, please read `CONTRIBUTING.md` and `CODE_OF_CONDUCT.md`.

---

## Before You Start

Before claiming an issue, make sure you have:

- Read the project's contribution guidelines.
- Set up the project locally.
- Explored the repository structure.
- Understood the issue requirements and acceptance criteria.
- Reviewed any existing discussion on the issue.

If you're contributing for the first time, begin with documentation or beginner-friendly issues to become familiar with the project workflow.

---

## Contributor Checklist

### Before Claiming an Issue

- [ ] Read the complete issue description.
- [ ] Check whether the issue is already assigned.
- [ ] Understand the expected solution.
- [ ] Ask questions if clarification is needed.

### During Development

- [ ] Create a dedicated branch for your work.
- [ ] Keep your changes focused on a single issue.
- [ ] Follow the project's coding and documentation standards.
- [ ] Test your changes before submitting.

### Before Opening a Pull Request

- [ ] Link the related issue (for example, `Closes #50`).
- [ ] Verify that your changes satisfy the acceptance criteria.
- [ ] Update documentation if required.
- [ ] Ensure formatting, linting, and tests (where applicable) pass successfully.
- [ ] Review your Pull Request description for clarity.

---

## Choosing the Right Issue

Select issues based on your experience and familiarity with the project.

- **`good-first-issue`** – Recommended for first-time contributors.
- **`beginner-friendly`** – Suitable for contributors learning the codebase.
- **`intermediate`** – Requires a good understanding of the project structure.
- **`advanced`** – Intended for experienced contributors working on larger features or architectural improvements.

### Best Practices

- Work on one issue at a time.
- Avoid claiming multiple issues simultaneously.
- Read the complete discussion before starting implementation.
- Communicate with maintainers whenever requirements are unclear.

---

## Pull Request Standards

A high-quality Pull Request should:

- Clearly explain the purpose of the change.
- Reference the related issue.
- Remain focused on a single objective.
- Follow the project's coding and documentation conventions.
- Include screenshots for UI changes when applicable.
- Respond promptly and professionally to review feedback.

For the complete review workflow, refer to **`docs/PR_WORKFLOW.md`**.

## Common Labels

The following labels are commonly used throughout the project:

| Label | Purpose |
| ------ | ------- |
| `good-first-issue` | Suitable for first-time contributors |
| `beginner-friendly` | Entry-level development tasks |
| `documentation` | Documentation improvements |
| `bug` | Bug fixes |
| `enhancement` | Feature enhancements |
| `frontend` | Frontend-related work |
| `backend` | Backend-related work |
| `hacktoberfest` | Eligible for Hacktoberfest |
| `mentor-available` | Mentor guidance is available |

For a complete description of all labels, see **`docs/LABELS.md`**.
